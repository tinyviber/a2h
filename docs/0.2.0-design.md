# A2H 0.2.0 — 设计

0.2.0 是 **「信任边界」版本**，同时把包更名为 `@tinyviber/a2h`。

关键在于这份设计的起点是一个容易被误读的事实：

> reviewer 提的四件事，在本轮开始之前**已经全部落在 `main` 上**（提交 `818fd73`，经 `755499a` 合入 PR #1）。
> 因此 0.2.0 并不是「新做四项工作」，而是**把这四项修复作为一个版本正式发布**，换到 scoped 包名，并把 CI 作为发布门禁。

**0.2.0 不含任何信任边界代码改动。** reviewer 明确要求「不要做其它大重构」；本轮新发现的加固点全部进入第 6 节的 backlog，不塞进这一版。

---

## 1. 为什么不能看提交标题

`818fd73` 的标题是 `fix: make effect policy authoritative on the provider side`，但它实际改了 **24 个文件 / +899 行**，一次性落地了 P0、P1、两个 P2 **以及 CI**。标题只描述了其中一项。

这是审计时最容易踩的坑：只看标题会得出「还有三项没做」的结论，然后重复劳动。任何后续 review 都应直接读 `git show 818fd73 --stat`，而不是读标题。

另有一处刻意不修的措辞差异：reviewer 写的接口名是 `resolve(action) -> { executor, simulated, effectPolicy }`，代码里的字段名是 **`policy`**（`src/providers/types.ts:70`，类型为 `EffectPolicy`）。语义一致，只是命名更短。保留 `policy`，避免为一个字段名引入歧义。

### 每项锁住的语义不变量

- **P0**：`manifest` 只能把 `state → external`，永远不能把 `external → state`；「离开本机必须确认」这条规则写在 `policy.ts` 内部，**不存在任何调用点可以绕过**（包括没有注册 provider 的纯 hint 路径）。engine 从 registry **重算**策略，而不是读传入的 `ActionView`，所以伪造的 view 也无法降级。
- **P1**：provenance 只允许往保守方向出错 —— `simulated = resolution.simulated || outcome.simulated`；executor 谎报「真实」不会让结果变成真实。
- **P2**：一个 section id 在整棵树里唯一，router 的 `find()` 不再是任意的。
- **P2**：URL 策略只有一份 allowlist，Markdown / list block / 未来的 block kind 只能引用它，不能各写一套。

## 3. 信任边界现在的形状

```text
危险等级（P0）
  manifest.sideEffect + confirm   ──┐  hint（不可信）
                                    ├─► strictestPolicy ─► 确认要求
  executor.policy(action)         ──┘  authoritative（即将运行的代码）

谁执行 / 是否模拟（P1）
  registry.resolve(action) ─► { executor, simulated, policy }   ← 唯一入口
  registry.allSimulated             ← 保留但不得用于标注单个 action

文件读取（review 上一轮已收敛）
  producer path ─► WorkspaceReader ─► allowlist ─► sensitive ─► symlink
                                    ─► realpath containment ─► bounded read

URL
  urlPolicy.isSafeLinkHref ─► server 剥离 ─► client 再剥离 ─► DOM
```

`workspaceRead` 这条链是 reviewer 唯一明确表扬的抽象（「不是 patchwork，而是架构改善」），0.2.0 不碰它。

## 4. 发布机制：0.2.0 的实际改动

| 文件 | 改动 | 验收 |
|---|---|---|
| `package.json` | `name` → `@tinyviber/a2h`；`version` → `0.2.0`；新增 `publishConfig: { "access": "public" }` | `npm pack --dry-run` 显示 `@tinyviber/a2h@0.2.0` |
| `package-lock.json` | 用 `npm install --package-lock-only` 重新生成（只改名与版本） | `npm ci` 在 CI 上通过 |
| `src/cli/index.ts` | `VERSION` → `'0.2.0'`；`--version` 输出改为 `@tinyviber/a2h ${VERSION}`；help 里 3 条示例改为 `npx @tinyviber/a2h ...` | `node bin/a2h.js --version` → `@tinyviber/a2h 0.2.0` |
| `README.md` | 9 处 `npx a2h` → `npx @tinyviber/a2h`；CLI 段用法行改为 scoped 形式；补一句「安装后命令名仍是 `a2h`」 | 人工通读 |
| `scripts/copy-assets.js` | 日志前缀 `[a2h]` → `[@tinyviber/a2h]` | 构建输出 |
| `CHANGELOG.md` | 新增，记录 0.2.0 / 0.1.0 | 文件存在且四项均有条目 |

### `publishConfig.access` 是必需的，不是可选的

scoped 包默认以 **restricted（私有）** 发布。在未购买私有包额度的账号上，`npm publish` 会直接失败；更糟的情况是发布成功但没人能安装。显式写 `"public"` 是这一步唯一的正确做法。

### `npx a2h` 必须一起改

包名变成 `@tinyviber/a2h` 之后，`npx a2h` 会去拉**另一个无 scope 的同名包**，而不是本项目。命令名（`bin` 的 key）与包名是两件事：`bin` 保持 `a2h`，调用方式变成 `npx @tinyviber/a2h`，全局安装后仍然是 `a2h`。

### 刻意不改（协议契约）

改名只动 npm 包，**不动任何磁盘/线上契约**：

`.a2h/` 目录 · `a2h.json` · manifest 里的 `"a2h": 1` 版本字段 · `x-a2h-token` / `a2h-token` 请求头 · `bin/a2h.js` 路径 · `a2h-img-missing` 样式名 · CLI help 的 usage 行（`a2h [render] [path] [options]`，因为它描述的是运行时命令名）。

## 6. 延后到后续版本的加固 backlog

按优先级排序。**这些都不进 0.2.0**：它们要么超出「不要做其它大重构」的授权，要么会破坏既有公共 API。

1. **href 策略改为按 shape 强制**（P2，前向风险）
   现在只在 `block.type === 'list'` 分支剥离（`src/presentation/blocks.ts:67`）。当前**不可利用**：整个协议里唯一的 `href` 是 `ListItem.href`（`src/types.ts:259`），且 client 还会再校验一次。但「任何 block kind 的 href 都必须过同一道闸」目前并不成立。
   建议：把 `resolveBlock` 的 list 分支换成递归 walker，对任意 `href` 键统一走 `isSafeLinkHref`。

2. **producer 声明的 run 仍然无条件自称「真实」**（P2，同一类不诚实 provenance）
   `toRunView` 硬编码 `simulated: false`（`src/semantics/resolve.ts:241`）。P1 修的是 action 的 provenance，run 这一侧还没有权威来源。
   建议：加 `RunView.source: 'producer' | 'execution'`，engine 产出的 run 标 `execution` 并给真实 `simulated`，manifest 声明的 run 标 `producer`。这是**协议增量**，所以不适合塞进一个纯发布的版本。

3. **两个「已声明」的 group 同 id 会静默合并**（P3）
   `mergeSectionsById` 只在「explicit 折入 inferred」时告警（`src/ir/build.ts:243`）。两个显式 group 撞 id 时无任何提示，第一个赢。
   建议：只要第二个同 id 节点到来就告警。
   注意：显式 group 没有任何 artifact 时被丢弃是**有意行为**（`test/presentation.test.ts:166` 有断言），不是 bug。

4. **`ProviderRegistry.allSimulated` 保留不删**（P3）
   它是导出的公共 API，且 `test/actions.test.ts:413` 直接断言 `createDefaultRegistry().allSimulated === true`。要删必须同时改测试与任何下游实现者 —— 属于独立的 minor 变更，不该混进改名版本。per-action 的 `resolve()` 才是正确入口，接口注释已经写明「不要用它标注单个 action」。

5. **真实 provider executor 仍然缺席**（P3，reviewer 明确延后）
   `createWorkBuddyExecutor` 目前只是 `src/providers/registry.ts:8` 的一行注释。reviewer 要的是 **seam 正确**，集成在后续。0.2.0 不引入任何网络传输、凭据或持久化。

6. **可选：廉价的改名防漂移守卫**（P3）
   断言 `package.json` 的 `name`/`version` 与 CLI 的 `VERSION` 常量一致。改名是本版唯一的新增表面，目前只有人工门禁。属于「值得有」，不阻塞。

## 7. 验证记录（实测）

在 `main` + 本版改动上实跑。环境：macOS，Node 22.22.2，`publishConfig` 与 scoped 包名均已生效。

| 门禁 | 命令 | 结果 |
|---|---|---|
| 构建 | `npm run build` | `tsc` 通过；输出 `[@tinyviber/a2h] copied renderer assets to …/dist/renderer/assets` |
| 单测 | `npm test` | **208 passed / 10 files**，连续三次 exit 0 |
| 版本 | `node bin/a2h.js --version` | `@tinyviber/a2h 0.2.0` |
| 打包 | `npm pack --dry-run` | `name: @tinyviber/a2h`、`version: 0.2.0`、`tinyviber-a2h-0.2.0.tgz`、166 files |
| 浏览器验收 | `node test/acceptance.cjs --ws … --profile …` × 3 | mixed **33** + radar **49** + coding **31** = **113 passed, 0 failed** |

三点说明：

- `113` 与 reviewer 引用的旧 PR 自报值一致，但这次是可复现的本地结果；CI 会对同一组 profile 再跑一遍，之后这个数字才由 CI 而不是由人声明。
- 期间出现过一次 8 个用例失败的运行（`collect` 阶段从约 2s 涨到 29s，疑似与另一个 Vitest 进程重叠造成的资源争用），随后连续三次全绿。**结论：环境性失败，不是回归**；复现注意事项是测试要串行跑，不要并行。
- 未跑：`npm publish`（外部动作，待你确认 npm org 权限）。`main` 上的 CI 已连续三次全绿（run 见第 5 节）；0.2.0 的这一版仍需自己跑一遍，见第 8 节建议 2。

## 8. 最终建议（5 条）

1. **把 0.2.0 当作「发布既有修复」而不是「修 bug」**：四项已在 `main`，本版的价值在于版本语义、包名和 CI 门禁，不在于新增代码量。
2. **合并前确认一次真实的 CI run**：这是 reviewer 唯一的流程性要求，而本版改动是元数据 + 文档，代价最低。
3. **发布后核对 `@tinyviber/a2h` 的 public 可见性**：确认 npm org `tinyviber` 存在且你有发布权限，否则 `npm publish` 会在权限上失败而不是在配置上失败。
4. **把 backlog 第 1、2 条合成下一个版本的主题**：「provenance 与 URL 策略不再有例外」——它们和本版是同一条思路的收尾，但需要一个带协议增量的版本。
5. **不要重命名协议标识符**：`.a2h/`、`a2h.json`、`"a2h": 1`、`x-a2h-token` 是 producer 已经依赖的契约；包名和协议名在这里必须解耦。
